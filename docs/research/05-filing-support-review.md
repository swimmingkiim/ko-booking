# 5단계: 홈택스 제출 지원 검토

조사일: 2026-11-21 (한국 시간). 범위는 개인사업자의 2025년 귀속 종합소득세 간편장부 신고다. **공식 신고 절차 확인과 연동 설계까지 수행했으며, 변환파일 생성·제출 기능은 구현하지 않았다.**

## 결론

현재 거래 CSV는 거래 정리·검토용이다. 이를 종합소득세 변환파일로 바로 변환하거나 업로드 가능하다고 안내할 근거는 없다. 우선 장부에서 신고서 작성에 필요한 집계·누락 항목을 확인하는 보조 기능을 만들고, 공식 변환명세를 확보·검증한 뒤 파일 어댑터를 구현한다. 홈택스 제출·접수, 지방소득세 신고, 납부는 각각 별도로 관리한다.

## 신고 화면과 현재 데이터의 차이

다음은 PDF 9~10쪽과 현 코드 `Ledger.summarize`, `Ledger.export`를 비교한 설계 판단이다. 화면 항목은 변환파일의 레코드 정의와 동일하다고 가정하지 않는다.

| 신고서 작성에 필요한 구분 | 현재 앱에서 얻을 수 있는 자료 | 구현 전 보완 |
| --- | --- | --- |
| 장부상 매출·기타 수입 | 연도별 분류·장부 금액·부가세 | 자산매각 등 항목별 수입 귀속 검토, 사업장·업종 식별 |
| 매출원가 | 상품매입 분류 | 기초·기말 재고와 제조비용. 상품매입 지출을 매출원가로 그대로 대입하지 않음 |
| 일반관리비 | 분류별 금액, 분할·환불 기록 | 공식 항목별 매핑, 기타경비의 세분화, 감가상각 등 비현금 경비 |
| 장부상 금액의 세무조정 | 없음 | 수입·경비의 제외·가산, 기부금 관련 조정 및 근거 |
| 종합소득세 전체 신고 | 일부 계산요소만 있음 | 다른 소득, 공제·감면, 가산세, 원천징수·기납부세액 등 |

공식 매뉴얼은 장부 집계 다음에 소득금액 조정을 거쳐 전체 신고서를 완성하는 흐름을 보여준다. 따라서 대시보드의 수입·비용 차액을 신고 소득금액이나 납부세액으로 사용할 수 없다. 세부 입력은 PDF의 해당 화면을 확인한다.

## 어댑터 설계안 — 아직 구현하지 않음

장부 도메인과 홈택스 물리 파일 규격을 분리한다. 초기 구현은 `prepare`와 `validate`에 한정하고, 원문 명세와 합성 검증 사례를 확보하기 전에는 `serialize`를 활성화하지 않는다.

| 경계 | 입력 | 출력·책임 |
| --- | --- | --- |
| `prepare` | 한 시점의 장부·거래 리비전, 귀속연도, 과세유형, 사용자 보완 입력 | 신고 준비 스냅샷. 원본 거래 ID·분할 순번과 집계 근거 보존 |
| `validate` | 스냅샷, 검토한 계산 규칙, 명세 버전 | 누락·미지원·불일치 목록. 미확인을 0으로 채우지 않음 |
| `serialize` | 검증 통과한 스냅샷, 고정한 공식 변환명세 | 바이트 파일·SHA-256·생성기 버전. 실제 지원 세목·연도·신고유형만 허용 |
| `record_result` | 사용자 확인 또는 검증된 접수자료 | 제출 시도와 증거 기록. 파일 생성만으로 접수 완료 처리하지 않음 |

스냅샷 메타데이터 제안:

- `schema_version`, `snapshot_id`, `created_at`, `tax_year`, `filing_type`, `business_id`.
- `ledger_fingerprint`, `transaction_revisions`, `vat_mode`, `calculation_rule_version`.
- `spec_title`, `spec_revision`, `spec_source_url`, `spec_sha256` (미확보면 null).
- `field_values`: 금액은 원 단위 십진 정수 문자열. 미확인값 null과 확인된 0을 구분.
- `provenance`: 항목별 거래·분할 연결, 수동 조정값·사유·검토 시각.
- `blocking_issues`: 항목 경로, 오류 코드, 설명. 예: `SPEC_UNVERIFIED`, `INVENTORY_UNCONFIRMED`, `UNSUPPORTED_INCOME`.

현재 `ledger_fingerprint`는 해당 연도 거래 ID·리비전과 과세유형으로 구성된다. 향후 신고 스냅샷 해시는 여기에 사업장 식별·수동 입력·규칙·명세 버전까지 포함해야 한다. 장부 검토 완료는 신고 준비 완료와 별개다. DB에서 읽는 중 변경이 섞이지 않도록 한 트랜잭션에서 스냅샷을 생성한다.

## 제출·접수 상태 설계안

아래 이름은 앱 내부 상태 제안이며 홈택스가 제공하는 상태 코드가 아니다.

| 상태 | 진입 조건 | 다음 처리 |
| --- | --- | --- |
| `draft` | 작성 시작 또는 검토 자료 변경 | 누락·조정 확인 |
| `prepared` | 준비 자료와 사용자 보완 입력 검토 완료 | 명세 검증 |
| `file_validated` | 구현된 명세 검증 통과 | 파일 생성·사용자 전달. 접수 완료로 표시하지 않음 |
| `submission_unknown` | 제출 시도는 있었으나 결과 증거 없음 | 신고내역 확인 후 재제출 여부 판단 |
| `submitted_unverified` | 사용자가 제출했다고 기록 | 접수증 대조 |
| `receipt_verified` | 접수번호·귀속연도·세목·신고유형·대상자·해당 스냅샷 일치 확인 | 증빙·지방세·납부 상태 별도 관리 |
| `rejected` | 형식·내용 오류 또는 명시적 제출 실패 확인 | 오류를 보존하고 새 리비전 작성 |

매뉴얼 PDF 35~37쪽은 신고서 제출 후 접수증·신고내역 확인, 필요한 증빙 제출, 별도 지방소득세 신고를 안내한다. 앱에서는 파일 검증 성공, 신고서 접수, 증빙 첨부 완료, 지방소득세 신고, 납부를 하나의 완료 표시로 합치지 않는다. 수동으로 기록한 완료는 검증된 접수와 구분한다.

접수 기록 설계 시 `attempt_id`, `snapshot_id`, `file_hash`, 채널·시각, 확인 방식, 접수번호와 증거 파일 해시를 저장한다. 결과가 불명확한 시도는 자동 재전송하지 않는다. 기존 접수 이후 장부를 고치면 기존 증거를 덮어쓰지 않고 새 준비 리비전과 연결한다. 수정신고·경정청구·기한후신고의 전이 규칙은 이번 범위에서 정의하지 않았다.

## 명세 확보 후 확인할 사항

1. 자료실 1246번 일반신고서 DOCX를 확보하고 원문 해시·수집일·게시물 변경일을 고정한다. 실제 귀속연도·명세 버전과 적용 신고유형을 원문에서 대조한다.
2. 필수 레코드, 항목 위치·바이트 길이, 한글 인코딩, 숫자·부호·공란·줄바꿈, 파일명·코드표·합계 검증을 원문에 따라 추출한다. 아직 어떤 방식도 확정하지 않았다.
3. 사업장 정보·간편장부 관련 서식과 전체 신고 필수 서식의 의존성을 확인한다. 원천세·부가세·분리과세 파일 명세를 혼용하지 않는다.
4. 자체 개발 프로그램의 현행 등록·적합성 검증 조건, 검증 도구·테스트 환경, 이용조건을 공식 자료로 확인한다. 과거 안내를 현재 요건으로 단정하지 않는다.
5. 합성 사례의 정상·누락·금액 경계·한글 바이트 경계·구버전 거부를 테스트한다. 홈택스 형식·내용 검증 결과를 확보하기 전에는 호환 완료로 표시하지 않는다.

공개 제출 API의 공식 계약·인증·이용조건은 이번 조사에서 확인하지 못했다. API가 없다고 단정하지 않으며, 내부 웹 요청을 공개 API로 취급하지 않는다. 이번에는 인증정보 입력·신고자료 전송·실제 제출·납부를 수행하지 않았다.
