# 5단계: 홈택스 제출 지원 검토

조사일: 2026-11-21 (한국 시간). 범위는 개인사업자의 2025년 귀속 종합소득세 간편장부 신고다. **공식 자료 분석·신고 준비 진단·보완 입력과 필드 후보 매핑을 구현했으며, 변환파일 생성·제출 기능은 구현하지 않았다.**

## 결론

현재 거래 CSV는 거래 정리·검토용이다. 이를 종합소득세 변환파일로 바로 변환하거나 업로드 가능하다고 안내할 근거는 없다. 우선 장부에서 신고서 작성에 필요한 집계·누락 항목을 확인하는 보조 기능을 만들고, 공식 변환명세를 확보·검증한 뒤 파일 어댑터를 구현한다. 홈택스 제출·접수, 지방소득세 신고, 납부는 각각 별도로 관리한다.

## 신고 화면과 현재 데이터의 차이

다음은 PDF 9~10쪽과 현 코드 `Ledger.summarize`, `Ledger.export`를 비교한 설계 판단이다. 화면 항목은 변환파일의 레코드 정의와 동일하다고 가정하지 않는다.

| 신고서 작성에 필요한 구분 | 현재 앱에서 얻을 수 있는 자료 | 구현 전 보완 |
| --- | --- | --- |
| 장부상 매출·기타 수입 | 연도별 분류·장부 금액·부가세 | 자산매각 등 항목별 수입 귀속 검토, 사업장·업종 식별 |
| 매출원가 | 상품매입 분류 | 기초·기말 재고와 제조비용. 상품매입 지출을 매출원가로 그대로 대입하지 않음 |
| 일반관리비 | 분류별 금액, 분할·환불 기록 | 공식 항목별 매핑, 기타경비의 세분화, 감가상각 등 비현금 경비 |
| 장부상 금액의 세무조정 | 없음 | 수입·경비의 제외·가산, 기부금 관련 조정 및 근거 |
| 종합소득세 전체 신고 | 일부 계산요소만 있음 | 다른 소득, 공제·감면, 가산세, 원천징수·기납부세액 등 |

공식 매뉴얼은 장부 집계 다음에 소득금액 조정을 거쳐 전체 신고서를 완성하는 흐름을 보여준다. 따라서 대시보드의 수입·비용 차액을 신고 소득금액이나 납부세액으로 사용할 수 없다. 세부 입력은 PDF의 해당 화면을 확인한다.

## 원문 레코드 분석

기계 판독용 필드 목록은 [`filing-2025.json`](../../ko_booking/rules/filing-2025.json)에 저장했다. 원문 `word/document.xml`의 body 직계 요소를 0부터 센 위치도 기록했다. 모든 필드 위치는 1부터 시작하는 바이트 위치이며 누적 길이와 일치한다. 표의 실행·전송을 지시하는 문구는 자료로만 분석했다.

| 원문 절 | 자료구분·서식코드 | 길이·필드 수 | 반복 단위 |
| --- | --- | --- | --- |
| 27 간편장부소득금액계산서 | `52C115300` | 400바이트·22필드 | 소득구분코드·사업자등록번호 |
| 28 총수입금액및필요경비명세서 | `52C115400` | 650바이트·41필드 | 소득구분코드·사업자등록번호 |

두 레코드의 공통 앞부분은 자료구분 2, 서식코드 7, 소득구분코드 2, 사업자등록번호 10, 소재지 60, 주업종코드 6, 업종명 80바이트로 합계 167바이트다. 소득구분은 30·32·40이다. 숫자 금액은 NUMBER 13바이트다. 소재지·업종명은 Null 허용이고 나머지 공통 식별 항목은 Not null이다. 공란 필드는 SPACE다. 원문의 `default 0`은 제출 파일의 형식 요건으로 읽으며 앱의 미확인값을 0으로 바꿀 근거로 사용하지 않는다.

`C115300`은 금액 12개가 168~323바이트, 과세기간 시작·종료일이 각각 324~331·332~339바이트, 끝 공란 61바이트다. `C115400`은 과세기간이 467~474·475~482바이트에 있고, 그 뒤에도 감가상각비·차량유지비·지급수수료·소모품비·복리후생비·운반비·광고선전비·여비교통비가 13바이트씩 이어진다. 끝 공란은 64바이트다. 날짜가 나온 곳에서 레코드를 끝내거나 일반관리비 항목을 화면 순서대로 재배열하면 안 된다.

수록요령은 LINE SEQUENTIAL 및 레코드별 CR/LF, ASCII CODE, 한글 2바이트 완성형 KSC-5601을 명시한다. 따라서 현재 UTF-8 CSV와 형식이 다르다. EUC-KR/CP949의 허용 문자 차이, 숫자 부호·패딩·잘림 처리 및 바이트 경계는 후속 구현·검증 대상으로 남긴다. 파일명 예시에는 날짜·대표서식코드·신고구분이 있고 자유롭게 부여할 수 있다는 안내도 있으므로 예시를 유일한 필수 파일명으로 강제하지 않는다.

### 산식과 레코드 간 관계

표 순번으로 정규화한 산식이다. 후보 매핑에서 계산하며 미확인 입력이 하나라도 있으면 해당 산식은 null로 남긴다.

- C115400: 10 = 8 + 9, 14 = 11 + 12 − 13, 18 = 15 + 16 − 17, 21 = 18 + 19 + 20. 29는 22~28 및 33~40의 합, 30 = 14 + 29.
- C115300: 11 = 8 − 9 + 10, 15 = 12 − 13 + 14, 16 = 11 − 15, 19 = 16 + 17 − 18.
- 장부상 수입: C115300의 8과 C115400의 10, 장부상 필요경비: C115300의 12와 C115400의 30을 이름 기준으로 연결한다.
- 사업소득명세서 C110703 신고유형 20은 두 서식을 필수 부속서식으로 명시한다. 사업자번호·주업종·금액의 일치 검증이 필요하고 공동사업은 별도 조건이 있다. 단일 사업장만으로 모든 예외가 검증되는 것은 아니다.
- 파일 수록순서는 납세자별 51/52/53 C110700 이후 관련 소득·부속 레코드 순서를 제시한다. 두 간편장부 레코드만으로 완전한 신고 파일이 되지 않는다.

**원문 주석의 번호 불일치:** C115300의 장부상 수입 설명이 C115400 서식상 (12)를 합계로 참조하지만, C115400 표의 합계는 (13)이다. 필요경비 합계도 설명의 (32)와 표의 (41)가 다르다. C115400 설명은 C115300 장부상 수입·경비를 (10)/(14)로 참조하지만 표에서는 (11)/(15)다. 이름·산식·물리 위치를 함께 보존하고, 번호만 맞춰 강제 매핑하지 않는다. 홈택스 검증 사례나 공식 확인으로 해소하기 전 교차 서식 매핑은 검토 단계로 유지한다.

## 어댑터 설계와 구현 범위

장부 도메인과 홈택스 물리 파일 규격을 분리한다. 신고 준비 스냅샷과 현재 미지원 항목 진단을 `filing.py`에 구현했다. `filing_mapping.py`는 사업장·재고/원가·조정 보완 입력과 후보 매핑을 지원한다. 공식 전체 신고 검증과 `serialize`는 구현하지 않았다.

| 경계 | 입력 | 출력·책임 |
| --- | --- | --- |
| `prepare` | 한 시점의 장부·거래 리비전, 귀속연도, 과세유형, 사용자 보완 입력 | 신고 준비 스냅샷. 원본 거래 ID·분할 순번과 집계 근거 보존 |
| `validate` | 스냅샷, 검토한 계산 규칙, 명세 버전 | 누락·미지원·불일치 목록. 미확인을 0으로 채우지 않음 |
| `serialize` | 검증 통과한 스냅샷, 고정한 공식 변환명세 | 바이트 파일·SHA-256·생성기 버전. 실제 지원 세목·연도·신고유형만 허용 |
| `record_result` | 사용자 확인 또는 검증된 접수자료 | 제출 시도와 증거 기록. 파일 생성만으로 접수 완료 처리하지 않음 |

스냅샷 메타데이터 제안:

- `schema_version`, `snapshot_id`, `created_at`, `tax_year`, `filing_type`, `business_id`.
- `ledger_fingerprint`, `transaction_revisions`, `vat_mode`, `calculation_rule_version`.
- `spec_title`, `spec_revision`, `spec_source_url`, `spec_sha256` (미확보면 null).
- `field_values`: 금액은 원 단위 십진 정수 문자열. 미확인값 null과 확인된 0을 구분.
- `provenance`: 항목별 거래·분할 연결, 수동 조정값·사유·검토 시각.
- `blocking_issues`: 항목 경로, 오류 코드, 설명. 예: `SPEC_UNVERIFIED`, `INVENTORY_UNCONFIRMED`, `UNSUPPORTED_INCOME`.

현재 `ledger_fingerprint`는 해당 연도 거래 ID·리비전과 과세유형으로 구성된다. 향후 신고 스냅샷 해시는 여기에 사업장 식별·수동 입력·규칙·명세 버전까지 포함해야 한다. 장부 검토 완료는 신고 준비 완료와 별개다. DB에서 읽는 중 변경이 섞이지 않도록 한 트랜잭션에서 스냅샷을 생성한다.

| `draft` | 작성 시작 또는 검토 자료 변경 | 누락·조정 확인 |
| `prepared` | 준비 자료와 사용자 보완 입력 검토 완료 | 명세 검증 |
| `file_validated` | 구현된 명세 검증 통과 | 파일 생성·사용자 전달. 접수 완료로 표시하지 않음 |
| `submission_unknown` | 제출 시도는 있었으나 결과 증거 없음 | 신고내역 확인 후 재제출 여부 판단 |
| `submitted_unverified` | 사용자가 제출했다고 기록 | 접수증 대조 |
| `receipt_verified` | 접수번호·귀속연도·세목·신고유형·대상자·해당 스냅샷 일치 확인 | 증빙·지방세·납부 상태 별도 관리 |
| `rejected` | 형식·내용 오류 또는 명시적 제출 실패 확인 | 오류를 보존하고 새 리비전 작성 |

매뉴얼 PDF 35~37쪽은 신고서 제출 후 접수증·신고내역 확인, 필요한 증빙 제출, 별도 지방소득세 신고를 안내한다. 앱에서는 파일 검증 성공, 신고서 접수, 증빙 첨부 완료, 지방소득세 신고, 납부를 하나의 완료 표시로 합치지 않는다. 수동으로 기록한 완료는 검증된 접수와 구분한다.

접수 기록 설계 시 `attempt_id`, `snapshot_id`, `file_hash`, 채널·시각, 확인 방식, 접수번호와 증거 파일 해시를 저장한다. 결과가 불명확한 시도는 자동 재전송하지 않는다. 기존 접수 이후 장부를 고치면 기존 증거를 덮어쓰지 않고 새 준비 리비전과 연결한다. 수정신고·경정청구·기한후신고의 전이 규칙은 이번 범위에서 정의하지 않았다.

## 명세 검토 후 남은 확인 사항

1. 원문 확보·해시 및 V26.05 대조는 완료했다. 후속 개정 시 게시물 날짜와 첨부 해시를 다시 대조한다.
2. 간편장부 두 레코드의 위치·길이·공통 형식은 추출했다. 전체 신고 필수 레코드와 코드표, 숫자·부호·패딩의 실제 호환 검증은 남아 있다.
3. 사업장 정보·간편장부 관련 서식과 전체 신고 필수 서식의 의존성을 확인한다. 원천세·부가세·분리과세 파일 명세를 혼용하지 않는다.
4. 자체 개발 프로그램의 현행 등록·적합성 검증 조건, 검증 도구·테스트 환경, 이용조건을 공식 자료로 확인한다. 과거 안내를 현재 요건으로 단정하지 않는다.
5. 합성 사례의 정상·누락·금액 경계·한글 바이트 경계·구버전 거부를 테스트한다. 홈택스 형식·내용 검증 결과를 확보하기 전에는 호환 완료로 표시하지 않는다.

공개 제출 API의 공식 계약·인증·이용조건은 이번 조사에서 확인하지 못했다. API가 없다고 단정하지 않으며, 내부 웹 요청을 공개 API로 취급하지 않는다. 이번에는 인증정보 입력·신고자료 전송·실제 제출·납부를 수행하지 않았다.

## 신고 준비 진단 CLI (2026-11-21 후속 구현)

```sh
python -m ko_booking filing-prepare --year 2025 --ledger-db data/private/ledger.sqlite3
```

기존 웹앱 장부 DB를 읽기 전용으로 열어 JSON을 표준 출력한다. 웹앱에서 선택한 연도와 요청 연도가 다르면 실패하며 설정을 바꾸지 않는다. 존재하지 않는 DB나 공식 자료 카탈로그를 생성하지 않는다. JSON에는 거래·거래처 정보가 포함되므로 저장한다면 Git 제외 개인자료 경로를 사용한다. 이 출력은 홈택스 제출용 파일이 아니다.

출력에는 현재 장부 해시·거래 리비전·분류별 장부 금액·근거 행·미분류/부가세 확인 대상·제출 차단 사유가 들어간다. 제외 거래와 자산은 기존 장부 집계 정책을 유지하며, 상품매입을 신고 매출원가로 자동 변환하지 않는다. 미확인 장부 금액을 포함한 분류의 합계는 null이다. `snapshot_id`는 시각을 제외한 전체 진단 내용의 SHA-256으로 사업장 표시 이름·금액·리비전 변경도 반영한다.

사용자가 제공한 원문 해시와 범위를 담아 `content_verified=true`로 갱신했다. 이는 명시된 검토 범위에 한하며 `submission_format_validated=false`를 유지한다. `SPEC_UNVERIFIED` 진단은 `SPEC_IMPLEMENTATION_INCOMPLETE`로 교체했다. 다른 연도에는 2025년 명세를 붙이지 않는다. 규칙이 적용된 신고 계산 결과가 아니므로 `calculation_rule_version`도 null이다. 현재 `status=draft`, `submission_ready=false`는 항상 유지한다. 보완 입력이 없으면 사업장·원가·조정 미입력을 진단하고, 입력이 있으면 구체적 누락과 후보 매핑의 제약을 진단한다. 전체 신고·명세 구현 미완료 사유는 유지한다.

앞선 다운로드 실패는 사용자 원본 제공으로 해소되었다. 게시물과 원문 날짜·버전은 따로 보존한다.

## 사업장·원가·조정 보완 입력

현재는 **2025년 전체 과세기간·단일 사업장·소득구분 40(비임대 사업소득)**의 CLI 후보 매핑만 지원한다. 사업자번호 10자리·업종코드 6자리는 형식만 검사하며 실제 등록·업종 적용 자격은 검증하지 않는다. 공동사업·임대업·연중 개폐업·복수 사업장·전체 신고는 지원하지 않는다. 사업장 이름을 변경하거나 다른 사업장 DB를 사용한 경우 보완 입력도 다시 확인해야 한다.

1. 보완 입력 없이 진단을 실행해 최신 `ledger_fingerprint`를 얻는다.
2. [입력 틀](../../examples/filing-supplement-2025.json)을 `data/private/filing-supplement.json`에 복사한다. 이 틀은 사업장 정보가 비어 있어 그대로 실행할 수 없다.
3. 사업장 식별 정보·검토 사유·장부 해시를 입력하고 아래 필드별 금액과 사유를 채운다. 비어 있는 금액 사전은 미확인으로 남는다. 해당 없는 금액도 확인한 경우에만 문자열 `"0"`과 사유를 입력한다.
4. 다음 명령으로 진단 JSON을 확인한다. 장부 변경 후 예전 해시는 거부되므로 새 진단 기준으로 입력을 재검토한다.

```sh
python -m ko_booking filing-prepare --year 2025 --input data/private/filing-supplement.json
```

금액 입력의 공통 모양은 `"11": {"value": "10000", "note": "전기 기말재고와 대조"}`다. `value`는 13자리 이내의 음이 아닌 원 단위 정수 **문자열**, `note`는 비어 있지 않은 사유다. 숫자·불리언·소수·쉼표·음수·알 수 없는 키는 거부한다. 계산된 소득금액의 결손은 음수로 보존하고, 계산 결과의 자리수 초과도 진단한다. 이는 음수의 전자파일 부호 표현을 검증한 의미가 아니다.

| 입력 키 | 순번·의미 | 현재 처리 |
| --- | --- | --- |
| `business` | 사업자번호·업종·소득구분·소재지·업종명·과세기간·검토 사유 | 두 레코드 식별 필드 후보에 연결 |
| `expense_mapping` | 앞선 매핑 표의 분류별 후보 순번을 정수로 입력. 예: `"소모품비": 36` | 사용자가 확인한 분류만 연결. 누락된 비용 분류는 해당 필드를 미확인으로 둠 |
| `costs` | C115400의 11·12·13(원가), 15·16·17·19·20(제조비 구성) | 검토한 완성 금액을 입력. 상품매입을 직접 원가로 대체하지 않음 |
| `additional_expenses` | C115400의 22~28·33~40 | 장부에 없는 **추가** 비용만 입력. 연결한 장부 금액과 합산하며 장부 총액을 재입력하면 중복됨 |
| `adjustments` | C115300의 9·10·13·14·17·18 | 수입 제외·가산, 경비 제외·가산, 기부금 한도초과·이월 산입 |

장부 외 비용이 없음을 확인한 필드는 추가 비용 0을 명시해야 비용 합계가 확정된다. 상품매입·제조비용·감가상각은 사용자가 장부 및 별도 계산 자료와 대조해 입력한다. 자산 거래가 있으면 별도 검토 필요 진단을 유지한다. 제조비용 합계와 원가용 당기 매입/제조비용의 전용 여부는 자동 판정하지 않으며 사유에 조정·대조 근거를 기록한다.

보완 입력 사용 시 출력 스키마는 2이며 `candidate_mapping_version=2025-v26.05-1`이다. `candidate_records`는 서식코드별 표 순번의 값과 필드별 장부 행·수동 입력·산식 근거를 담는다. 예약 공란은 null로 두고 바이트 파일을 만들지 않는다. 원문 주석 번호 불일치에 따른 `CROSS_RECORD_MAPPING_PROVISIONAL`, 전체 신고 및 명세 구현 미완료 진단을 유지한다. 후보 소득금액은 과세표준·납부세액이 아니다. 보완 입력·사유·산식·버전도 스냅샷 해시에 포함한다.

## 완료·미완료 및 다음 작업

완료: 공식 자료 출처·확인 리비전 식별, 사용자 제공 원문 해시·부분 필드 명세 추출, 간편장부 데이터 매핑 후보와 주석 불일치 분석, 어댑터 경계·제출 상태 설계, 읽기 전용 신고 준비 진단 CLI, 사업장·원가·조정 보완 입력과 필드 후보 매핑 구현.

미완료: 전체 신고 명세 검증, 교차 서식 주석 불일치 해소, 웹 보완 입력 화면·파일 직렬화 어댑터, 홈택스 호환·접수 검증.

검증: 앞선 PDF 해시·화면 대조 기록 유지. 이번 DOCX는 두 표 63개 필드의 길이·누적 위치를 원문 XML과 대조했다. 한글 렌더링 제한은 위에 기록했다. 후속 구현은 장부 금액·근거 연결, 미확인 null 유지, 내용 해시 변경, 연도 격리, 장부 검토와 제출 준비의 구분, 읽기 전용·없는 DB 미생성, CLI 출력을 신규 7개 테스트로 검증했다. 추가 보완 입력 테스트 10개를 포함한 전체 테스트 72개, wheel 빌드·새 명세 리소스 포함, 문서 내부 링크·Git 공백 검사 통과. 이번에는 UI를 변경하지 않았다.
